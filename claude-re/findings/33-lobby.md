- The 430B op216 sub-packet IS the dynamic per-world population block (contains world indices matching the list + count-like values).
- BUT the field encoding is variable-length/smart, NOT fixed [u16][u8]: a fixed parse drifts (yields impossible totals/dupes).
- RETRACTED: any specific totals/busiest figures (a fixed parse gave garbage like 855k total/65k worlds - impossible). Exact per-world counts undetermined without the smart-encoding format.

## op216 LIVE world populations — VALIDATED (corrects iter32 retraction)
Format: [u8 hdr=0x01][per world: u16 count][SMART worldId]. (smart id = why fixed parse drifted; format per WORLDLIST_FETCH_REPLY@0x190020 + data-validated.)
- VALIDATION: consumes EXACTLY 430/430B, 0 dup ids, 132/132 strictly-increasing ids, **TOTAL ONLINE = 18127** (realistic RS3 ~18k).
- Busiest worlds (id,count): [(84, 1347), (56, 950), (14, 909), (79, 843), (64, 816), (70, 812), (123, 812), (0, 512), (3, 346), (7, 247)]
- 133 worlds with live counts -> matches the world-list hostnames/regions decoded earlier.

## World-def smart structure (per-world id/country/flags) — NOT reliably decoded (caught before recording)
- Attempted [smart id][smart country][smart flags][strings] parse of the 3001B world-defs packet -> DRIFTED.
- Region block is NOT [smart id][string]: a fixed `80 e1 00` prefix precedes each region name (misread as a smart id),
  truncating names ("nited States", "alia") and desyncing the world loop. Validation (vs known strings) caught it immediately.
- => per-world ids/flags/regions remain UNDETERMINED. RELIABLE world-list data = the STRINGS (names/addresses/activities/regions,
  already extracted) + the VALIDATED player counts (430B block). Not recording the drifted id/flag values.
